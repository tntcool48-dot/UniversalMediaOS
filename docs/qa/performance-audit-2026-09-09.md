## 1. P1 — Automatic playback repeats the same complete resolver

**Evidence.** `ResolveBestSourceAsync` calls `_scraper.ResolveAsync` for Tier 1 at [TripleNetHandoff.cs:107](C:/Users/user/animeapp/UniversalMediaOS.Core/Routing/TripleNetHandoff.cs:107). If it yields no source and the selected provider is blank/Automatic, the Tier 2 branch invokes `_scraper.ResolveAsync` again with the same query, episode, site budget, and audio preference at [TripleNetHandoff.cs:149](C:/Users/user/animeapp/UniversalMediaOS.Core/Routing/TripleNetHandoff.cs:149). There is no distinct browser-discovery mode supplied to that second invocation.

The normal Watch action reaches this route at [AnimeDetailsViewModel.cs:733](C:/Users/user/animeapp/UniversalMediaOS.WPF/ViewModels/AnimeDetailsViewModel.cs:733). Each invocation creates a new Python process at [ScraperEngine.cs:233](C:/Users/user/animeapp/UniversalMediaOS.Core/Services/ScraperEngine.cs:233), and Python launches a browser before sequentially traversing sites at [scraper.py:1874](C:/Users/user/animeapp/UniversalMediaOS.Core/scraper.py:1874). A resolver timeout is converted into an empty result, which allows the duplicate fallback to run, at [ScraperEngine.cs:290](C:/Users/user/animeapp/UniversalMediaOS.Core/Services/ScraperEngine.cs:290).

**Code-derived cost.** Default configuration is six site attempts at [DomainHotSwapper.cs:521](C:/Users/user/animeapp/UniversalMediaOS.Core/Configuration/DomainHotSwapper.cs:521). The process timeout formula is `clamp(25,000 + attempts × 8,000, 45,000, 120,000)` at [ScraperEngine.cs:181](C:/Users/user/animeapp/UniversalMediaOS.Core/Services/ScraperEngine.cs:181). This gives a 73-second timeout per default invocation, or 146 seconds across the duplicated path if both exhaust their process budgets. Configurations reaching the 120-second cap allow 240 seconds across the pair. These are process budgets; bootstrap, process startup, and bounded stream-drain cleanup are additional. Successful discovery may return much sooner.

**Reproduction condition.** Select Automatic provider, choose Auto stream, and use a title for which the first resolver exhausts its candidates. Logs should show two independent resolver starts for the same episode before a final failure.

**Fix.** Carry a single resolution result, including any discovered browser fallback, through the routing operation. If no candidate exists, return an actionable failure; run a second pass only if it uses meaningfully different inputs. Put one overall deadline around preparation and resolution. Track provider success per series/audio mode so episode navigation can try the previously working route first.

**Related behavior.** A chosen custom provider is not passed into the Tier 1 `_scraper.ResolveAsync` call. Native Auto streaming still searches the indexed pool first; the explicit provider is used later at [TripleNetHandoff.cs:191](C:/Users/user/animeapp/UniversalMediaOS.Core/Routing/TripleNetHandoff.cs:191). Trying the selected provider first would avoid a full indexed crawl when the user has already chosen a working source.

**Evidence.** Anime scraping awaits `_python.EnsureScraperReadyAsync` at [ScraperEngine.cs:199](C:/Users/user/animeapp/UniversalMediaOS.Core/Services/ScraperEngine.cs:199), then creates the operation timeout at [ScraperEngine.cs:212](C:/Users/user/animeapp/UniversalMediaOS.Core/Services/ScraperEngine.cs:212). All scraper consumers wait on the same readiness lock at [PythonBootstrapper.cs:77](C:/Users/user/animeapp/UniversalMediaOS.Core/Services/PythonBootstrapper.cs:77).

Nonzero pip exits and timeouts only generate warnings; setup then logs that all packages were verified. `_scraperReady` is assigned from executable and file existence, with no successful-import requirement or final recheck, at [PythonBootstrapper.cs:124](C:/Users/user/animeapp/UniversalMediaOS.Core/Services/PythonBootstrapper.cs:124). Settings independently labels the Python scraper Ready based only on `scraper.py` existing at [SettingsViewModel.cs:588](C:/Users/user/animeapp/UniversalMediaOS.WPF/ViewModels/SettingsViewModel.cs:588) and [SettingsViewModel.cs:620](C:/Users/user/animeapp/UniversalMediaOS.WPF/ViewModels/SettingsViewModel.cs:620).

**Code-derived cost.** If all five packages are missing and each install times out, the serial installation budgets total 300 seconds, before scraping starts. The combined import probe permits another 10 seconds at [PythonBootstrapper.cs:276](C:/Users/user/animeapp/UniversalMediaOS.Core/Services/PythonBootstrapper.cs:276). Startup does show the window before beginning service setup at [App.xaml.cs:70](C:/Users/user/animeapp/UniversalMediaOS.WPF/App.xaml.cs:70); this finding primarily explains delayed feature readiness and misleading health status, rather than a guaranteed five-minute frozen window.

**Reproduction condition.** Fresh Python environment, one or more missing packages, and unavailable/slow package download service. First scraper requests wait for setup, then can fail immediately on missing imports despite a Ready badge.

**Additional reliability detail.** Pip redirects both output streams at [PythonBootstrapper.cs:208](C:/Users/user/animeapp/UniversalMediaOS.Core/Services/PythonBootstrapper.cs:208), but waits for process exit before draining stderr at [PythonBootstrapper.cs:225](C:/Users/user/animeapp/UniversalMediaOS.Core/Services/PythonBootstrapper.cs:225), and never drains stdout. A sufficiently verbose pip/build failure can fill a pipe and block until its installation timeout. The import probe already demonstrates the correct concurrent-drain pattern at [PythonBootstrapper.cs:281](C:/Users/user/animeapp/UniversalMediaOS.Core/Services/PythonBootstrapper.cs:281).

**Fix.** Treat bootstrap as explicit, observable state: preparing, ready, or failed with the missing dependency identified. Bound total setup time, drain both streams concurrently, and verify imports after installation before setting readiness. Include preparation in each caller's total deadline. Prefer a packaged/pinned runtime or an explicitly maintained environment so normal feature use does not depend on installing packages.

## 3. P1 — HLS downloads can remain stuck after their advertised timeout

**Evidence.** The proxy uses a 30-second `HttpClient.Timeout` at [HlsLoopbackProxy.cs:84](C:/Users/user/animeapp/UniversalMediaOS.Core/Streaming/HlsLoopbackProxy.cs:84), but all three routes use `ResponseHeadersRead`. Manifest loading then reads the body without a cancellation token at [HlsLoopbackProxy.cs:396](C:/Users/user/animeapp/UniversalMediaOS.Core/Streaming/HlsLoopbackProxy.cs:396); segment streaming does the same at [HlsLoopbackProxy.cs:447](C:/Users/user/animeapp/UniversalMediaOS.Core/Streaming/HlsLoopbackProxy.cs:447) and [HlsLoopbackProxy.cs:474](C:/Users/user/animeapp/UniversalMediaOS.Core/Streaming/HlsLoopbackProxy.cs:474); key loading does the same at [HlsLoopbackProxy.cs:486](C:/Users/user/animeapp/UniversalMediaOS.Core/Streaming/HlsLoopbackProxy.cs:486). The helper's default token is never tied to a playback/session deadline.

`ResponseHeadersRead` makes the HttpClient timeout stop applying once headers arrive; body reading requires its own timeout. This behavior is documented by [Microsoft's HttpCompletionOption reference](https://learn.microsoft.com/en-us/dotnet/api/system.net.http.httpcompletionoption?view=net-10.0).

Each incoming request launches an untracked task at [HlsLoopbackProxy.cs:313](C:/Users/user/animeapp/UniversalMediaOS.Core/Streaming/HlsLoopbackProxy.cs:313). Proxy disposal stops the listener but does not cancel active outbound reads at [HlsLoopbackProxy.cs:976](C:/Users/user/animeapp/UniversalMediaOS.Core/Streaming/HlsLoopbackProxy.cs:976).

**Impact/reproduction condition.** A CDN sends HTTP headers and then stalls partway through a manifest, key, or segment. The app's own 30-second timeout does not terminate that body read. Playback can stay buffering, and retries/source switches can accumulate in-flight requests. OS/TCP behavior may eventually end a connection; there is no application-defined body deadline here.

**Fix.** Give manifest/key requests an end-to-end deadline and segment streams an inactivity timeout appropriate to streaming. Link reads to proxy and playback-session cancellation; terminate requests when their session closes. Track active requests and bound concurrent work. Avoid using a short fixed total timeout for an entire long movie file; reset an inactivity budget as useful bytes arrive.

## 4. P2 — Dub search withholds every card until all availability checks finish

**Evidence.** Search retrieves 36 metadata results, then awaits `ApplyAudioFilterAsync` before replacing the visible result collection at [SearchViewModel.cs:321](C:/Users/user/animeapp/UniversalMediaOS.WPF/ViewModels/SearchViewModel.cs:321). The Dub branch creates a check per result with concurrency four and waits for all of them at [SearchViewModel.cs:474](C:/Users/user/animeapp/UniversalMediaOS.WPF/ViewModels/SearchViewModel.cs:474) and [SearchViewModel.cs:502](C:/Users/user/animeapp/UniversalMediaOS.WPF/ViewModels/SearchViewModel.cs:502). Recommendation and load-more paths use the same barrier.

However, provider HTTP work is serialized per host at [DubAvailabilityService.cs:1151](C:/Users/user/animeapp/UniversalMediaOS.Core/Services/DubAvailabilityService.cs:1151), with a 350 ms spacing policy at [DubAvailabilityService.cs:141](C:/Users/user/animeapp/UniversalMediaOS.Core/Services/DubAvailabilityService.cs:141). The built-in provider performs one search request per uncached summary at [DubAvailabilityService.cs:553](C:/Users/user/animeapp/UniversalMediaOS.Core/Services/DubAvailabilityService.cs:553). Four view-model workers do not produce four simultaneous requests to that host.

**Conditional calculation.** With 36 uncached titles all successfully requiring one request to the same host and no intervening timeout/backoff, the 35 spacing intervals alone total 12.25 seconds, plus network/body work and the metadata request. This is not a measured latency and is not a universal worst-case bound: cache hits reduce it, while retries or extra configured providers change it. The provider already has timeouts and backoff, so claiming every search always waits `36 × 10 seconds` would be incorrect.

**Scope.** This barrier is specific to Audio = Dub. The default Any path returns metadata immediately at [SearchViewModel.cs:469](C:/Users/user/animeapp/UniversalMediaOS.WPF/ViewModels/SearchViewModel.cs:469). Automatic badge annotation is already limited to visible rows and capped at 12 per search; retain those protections.

**Fix.** Keep metadata visible while availability arrives; label unchecked items and progressively remove confirmed nonmatches or present confirmed matches as they complete. Use cached availability immediately. Preserve host throttling instead of increasing network concurrency indiscriminately.

## 5. P2 — Book search waits for its slowest provider and mishandles timeouts

**Evidence.** The book catalog launches all providers and waits for every one before merging or returning anything at [BookCatalogService.cs:41](C:/Users/user/animeapp/UniversalMediaOS.Core/OtherMedia/Books/BookCatalogService.cs:41). The normal application registers Open Library, Google Books, and Anna's Archive at [App.xaml.cs:374](C:/Users/user/animeapp/UniversalMediaOS.WPF/App.xaml.cs:374). Anna's Archive always calls the Python search engine for a nonempty query at [AnnasArchiveBookProvider.cs:41](C:/Users/user/animeapp/UniversalMediaOS.Core/OtherMedia/Books/AnnasArchiveBookProvider.cs:41). Its search process permits 25 seconds at [BookScraperEngine.cs:46](C:/Users/user/animeapp/UniversalMediaOS.Core/OtherMedia/Books/BookScraperEngine.cs:46), after the shared setup described in finding 2.

**Impact.** Fast public-catalog results remain invisible while a slow scraper works. The grid is only populated after the combined call returns at [BookBrowseViewModel.cs:241](C:/Users/user/animeapp/UniversalMediaOS.WPF/ViewModels/BookBrowseViewModel.cs:241). The Python budget alone can add a 25-second wait; this is not an upper bound for the combined search.

**Timeout correctness.** Open Library and Google Books preserve caller cancellation and handle HTTP/JSON failures, but do not handle `OperationCanceledException` caused by their own HttpClient timeout: [OpenLibraryBookProvider.cs:94](C:/Users/user/animeapp/UniversalMediaOS.Core/OtherMedia/Books/OpenLibraryBookProvider.cs:94), [GoogleBooksBookProvider.cs:146](C:/Users/user/animeapp/UniversalMediaOS.Core/OtherMedia/Books/GoogleBooksBookProvider.cs:146). The catalog wrapper has the same gap at [BookCatalogService.cs:131](C:/Users/user/animeapp/UniversalMediaOS.Core/OtherMedia/Books/BookCatalogService.cs:131). One provider timeout therefore faults the aggregate and prevents successful results from other providers being returned. The view model silently catches all cancellation exceptions at [BookBrowseViewModel.cs:261](C:/Users/user/animeapp/UniversalMediaOS.WPF/ViewModels/BookBrowseViewModel.cs:261), leaving blank/previous results and the searching status text rather than explaining the provider timeout.

Both public providers also use `ResponseHeadersRead` followed by a JSON body parse with no body-specific deadline: [OpenLibraryBookProvider.cs:54](C:/Users/user/animeapp/UniversalMediaOS.Core/OtherMedia/Books/OpenLibraryBookProvider.cs:54), [GoogleBooksBookProvider.cs:106](C:/Users/user/animeapp/UniversalMediaOS.Core/OtherMedia/Books/GoogleBooksBookProvider.cs:106). The same Microsoft timeout semantics cited in finding 3 apply.

**Reproduction condition.** Supply one provider that returns a valid page immediately and another that times out or sends headers then stalls. Observe that no partial page is delivered; the timeout case is treated by the UI like user cancellation.

**Fix.** Return/display pages as providers finish, with per-provider status and failures. Separate caller cancellation from provider timeout; retain all successful pages. Give each provider an overall request budget including body parsing and, where applicable, preparation. Ensure a slow optional scraper does not gate the first useful catalog view.

## 6. P2 — Poster requests outlive views and can wait indefinitely on body data

**Evidence.** `AsyncImageLoader` has an 18-second client timeout at [AsyncImageLoader.cs:23](C:/Users/user/animeapp/UniversalMediaOS.WPF/Controls/AsyncImageLoader.cs:23), then uses `ResponseHeadersRead` at [AsyncImageLoader.cs:99](C:/Users/user/animeapp/UniversalMediaOS.WPF/Controls/AsyncImageLoader.cs:99). Its body-read loop uses a token with no deadline at [AsyncImageLoader.cs:120](C:/Users/user/animeapp/UniversalMediaOS.WPF/Controls/AsyncImageLoader.cs:120). The token is cancelled only when that image's URL changes at [AsyncImageLoader.cs:66](C:/Users/user/animeapp/UniversalMediaOS.WPF/Controls/AsyncImageLoader.cs:66); the loader does not subscribe to `Unloaded` or link cancellation to a view lifetime.

Every cache miss immediately starts its own request. There is a completed-image LRU cache, but no global request concurrency limit or same-URL in-flight coalescing in [AsyncImageLoader.cs:79](C:/Users/user/animeapp/UniversalMediaOS.WPF/Controls/AsyncImageLoader.cs:79). A request's asynchronous state retains its target Image until it completes/cancels. Rapid view replacement can therefore keep downloading posters for detached views; a stalled body can retain them indefinitely at the application level. Duplicate visible images can fetch the same URL concurrently.

**Positive existing controls.** The loader already decodes off the UI thread, downsamples, caps individual compressed responses at 25 MB, and keeps only 150 completed cached images. The search grid already uses recycling virtualization. Those mitigations help ordinary scrolling and should be retained; they do not cancel stalled or detached image requests.

**Fix.** Add an end-to-end image deadline, cancel on image unload, and restart when a still-bound image is loaded again. Limit download/decode concurrency and share in-flight fetches by URL, using subscriber-aware cancellation. Keep current decode sizing, response-size cap, and cache bounds.

## 7. P2 — SQLite still executes on UI paths despite async method names

**Evidence.** Opening playback adds the tab and calls `LoadMedia` synchronously at [MainViewModel.cs:365](C:/Users/user/animeapp/UniversalMediaOS.WPF/ViewModels/MainViewModel.cs:365). Resume configuration calls `LoadResumePosition` at [PlaybackViewModel.cs:1872](C:/Users/user/animeapp/UniversalMediaOS.WPF/ViewModels/PlaybackViewModel.cs:1872). That method performs a blocking semaphore wait, schema check, and synchronous database lookup at [PlaybackViewModel.cs:1946](C:/Users/user/animeapp/UniversalMediaOS.WPF/ViewModels/PlaybackViewModel.cs:1946). Switching media synchronously saves the old position at [PlaybackViewModel.cs:564](C:/Users/user/animeapp/UniversalMediaOS.WPF/ViewModels/PlaybackViewModel.cs:564); disposal also synchronously persists resume data at [PlaybackViewModel.cs:2533](C:/Users/user/animeapp/UniversalMediaOS.WPF/ViewModels/PlaybackViewModel.cs:2533).

Each save/load rechecks database creation at [PlaybackViewModel.cs:2155](C:/Users/user/animeapp/UniversalMediaOS.WPF/ViewModels/PlaybackViewModel.cs:2155). VA operations also run multiple synchronous schema statements via `EnsureVaDetectSchema`, including calls made before the first await in [VoiceActorIndexService.cs:35](C:/Users/user/animeapp/UniversalMediaOS.Core/Services/VoiceActorIndexService.cs:35) and [VoiceCastService.cs:62](C:/Users/user/animeapp/UniversalMediaOS.Core/Services/VoiceCastService.cs:62). The schema method is at [DatabaseContext.cs:200](C:/Users/user/animeapp/UniversalMediaOS.Core/Data/DatabaseContext.cs:200).

Changing these calls to `SaveChangesAsync`/`ToListAsync` alone does not move SQLite disk work off the dispatcher: [Microsoft documents that Microsoft.Data.Sqlite's async ADO.NET methods execute synchronously](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/async).

**Impact/reproduction condition.** Slow storage, a configured database on a slow path, a first schema initialization, or concurrent writes can cause visible stalls during playback transitions. Semaphore waits permit two seconds at [PlaybackViewModel.cs:2094](C:/Users/user/animeapp/UniversalMediaOS.WPF/ViewModels/PlaybackViewModel.cs:2094); SQLite busy timeout is configured as five seconds at [DatabaseContext.cs:161](C:/Users/user/animeapp/UniversalMediaOS.Core/Data/DatabaseContext.cs:161). These are separate mechanisms, not a measured or strict combined maximum. No claim is made that the normal local database currently causes multi-second pauses.

**Fix.** Initialize/migrate schema once per database lifecycle. Perform storage work on a dedicated background queue using contexts owned by that queue, then publish results to the dispatcher. Coalesce resume writes and await a bounded final flush during asynchronous close. Do not share a single DbContext across overlapping worker operations.

## Verification needed before attributing the user's observed latency

The next diagnostic pass should record time to first useful content separately from time to finish all background work: window shown, first anime cards, Dub completion, book provider arrivals, Python ready, first resolver candidate, and first playback frame. Run a warm-cache and cold-cache comparison. Capture UI thread activity during playback tab open/close to distinguish dispatcher stalls from asynchronous network waiting.

Focused regression scenarios for the fixes are: a failed resolver must be invoked only once; a failed dependency install must not report Ready; headers-then-stalled-body must be cancelled in HLS/images/books; a fast book provider must remain visible when another times out; Dub filtering must provide useful UI before all checks finish; and database contention must not block the dispatcher. These scenarios were proposed, not executed in this read-only audit.

Existing safeguards observed during review include scoped disposable tab view models, explicit search lifecycle cancellation/generation checks, recycled search rows, off-thread poster decoding, provider-level dub throttling/backoff and in-flight lookup sharing, and an eight-second uBlock setup timeout. Consequently, the older claims that all tabs necessarily leak, all images decode on the UI thread, or uBlock setup still waits the default 100 seconds should not be repeated without new evidence.
