# WPF UI audit — 2026-09-09

History follow-up: the [Git and task comparison](C:/Users/user/animeapp/docs/qa/git-and-task-history-comparison-2026-09-09.md) recovers the June tabbed shell's left/right grouping, traces wrapping navigation to the July 18 frontend cleanup, and finds that the global dropdown width was added during the earlier June design task.

The reported crowding has a concrete cause in the application shell. All destinations, including Settings, were moved into one wrapping navigation strip. The shared ComboBox style also contains two independently reproduced sizing/template defects. Button hover and light-theme colors introduce additional readability failures.

This is a read-only production-code audit. Verification used the current XAML resource dictionaries and WPF layout/rendering through PowerShell; it did not launch network services, alter application settings, or run the full test suite. The source checkout already contains extensive uncommitted changes, so these findings identify the current implementation and its difference from HEAD without attributing individual changes to a particular model or run. Citation line numbers were rechecked on 2026-09-09.

## 1. P2 — Settings shares the crowded media navigation strip and wraps onto a row by itself

Evidence: [MainWindow.xaml:156](C:/Users/user/animeapp/UniversalMediaOS.WPF/MainWindow.xaml:156) contains a single default-left `WrapPanel` for all 12 destinations. [MainWindow.xaml:168](C:/Users/user/animeapp/UniversalMediaOS.WPF/MainWindow.xaml:168) places the Settings icon as its last child. There is no separate utility area, flexible spacer, or grouping for the app-wide actions.

The exact navigation markup and its styles were measured using WPF. Only localization markup was replaced with its English labels and commands removed from the isolated probe; layout values were retained.

| Available width | Navigation height | Settings position | Result |
| --- | --- | --- | --- |
| 1280 DIP | 42.96 DIP | x=878.0, y=6.0 | All controls occupy x=8.0 through about 910.2; about 370 DIP remains empty on the right. |
| 900 DIP | 72.96 DIP | x=8.0, y=42.0 | Settings alone moves to a second row. |

900 DIP is the application's supported minimum width, declared at [MainWindow.xaml:7](C:/Users/user/animeapp/UniversalMediaOS.WPF/MainWindow.xaml:7). The committed HEAD version used an explicit sidebar with Menu, Active, and System groups; the current working tree removes that hierarchy.

Practical fix: split primary media destinations and app-wide utility actions into distinct layout regions, keep Settings anchored with the utility actions, and define a compact-width overflow behavior. Use a constrained Grid or DockPanel layout rather than letting every destination compete in the same WrapPanel. The desired visual style remains a design decision; the one-sided positioning and solitary wrapped Settings row are measured behavior.

## 2. P2 — The global ComboBox minimum size overrides compact controls

Evidence: [Controls.xaml:174](C:/Users/user/animeapp/UniversalMediaOS.WPF/Themes/Controls.xaml:174) sets the shared input minimum height, and [Controls.xaml:175](C:/Users/user/animeapp/UniversalMediaOS.WPF/Themes/Controls.xaml:175) sets `MinWidth=220`. The same style is also applied implicitly to every ComboBox at [Controls.xaml:278](C:/Users/user/animeapp/UniversalMediaOS.WPF/Themes/Controls.xaml:278).

The player requests a 72×34 DIP speed selector at [PlaybackView.xaml:325](C:/Users/user/animeapp/UniversalMediaOS.WPF/Views/PlaybackView.xaml:325) and an 88×34 DIP quality selector at [PlaybackView.xaml:339](C:/Users/user/animeapp/UniversalMediaOS.WPF/Views/PlaybackView.xaml:339). WPF honors MinWidth/MinHeight ahead of these dimensions. Loading the real theme resources and measuring the speed selector produced an actual size of **220×38 DIP**. Both selectors therefore consume substantially more space than their surrounding toolbar expects.

The movie/TV/cartoon details view places a globally styled language selector inside a 170 DIP StackPanel at [AudiovisualCatalogView.xaml:469](C:/Users/user/animeapp/UniversalMediaOS.WPF/Views/AudiovisualCatalogView.xaml:469). Its minimum width exceeds the allotted column by 50 DIP, creating an overflow/clipping conflict beside the Refresh sources action. The source constraint is confirmed; the full detail-view overlap was not independently rendered in this sub-audit.

Practical fix: remove the 220 DIP minimum from the global base style and apply an appropriate minimum to individual full-size form fields. Provide compact selector metrics for playback. Verify the preferred-language selector fits its parent instead of relying on a fixed parent width to override the child's minimum.

## 3. P2 — ComboBox visual chrome is much smaller than its allocated control area

Evidence: [Controls.xaml:210](C:/Users/user/animeapp/UniversalMediaOS.WPF/Themes/Controls.xaml:210) embeds a normal ToggleButton in the ComboBox template without a dedicated template or stretched content alignment. Its Border and selection content are ordinary ToggleButton content at [Controls.xaml:216](C:/Users/user/animeapp/UniversalMediaOS.WPF/Themes/Controls.xaml:216).

The isolated WPF probe loaded `Tokens.xaml`, `Typography.xaml`, and `Controls.xaml` unchanged. For the speed selector with selected text `1x`:

- ComboBox actual width: **220 DIP**.
- ComboBox actual height: **38 DIP**.
- Nested ToggleButton horizontal content alignment: **Center**.
- Visible inner Border width: **61.97 DIP**.

This produces a small, inset pill inside a much larger allocated selector area. The result explains a concrete class of strange-looking controls independently of the minimum-width defect.

Probe image: [ui-audit-control-probe.png](C:/Users/user/animeapp/tmp/ui-audit-control-probe.png). This is an isolated rendering of the actual shared styles, not a screenshot of the running application. The second row is a PrimaryButton included as a visual reference.

Practical fix: give the toggle a simple dedicated ControlTemplate whose Border fills the available space, with stretched horizontal and vertical content alignment. Preserve the selection presenter, dropdown binding, keyboard behavior, and disabled/focus states. Merely removing MinWidth does not resolve the template's inset sizing behavior.

## 4. P2 — Shared hover and light-theme colors make button labels difficult to read

Evidence: the base button hover trigger forces the background to `#263449` at [Controls.xaml:51](C:/Users/user/animeapp/UniversalMediaOS.WPF/Themes/Controls.xaml:51), while PrimaryButton retains its foreground `#031412` at [Controls.xaml:70](C:/Users/user/animeapp/UniversalMediaOS.WPF/Themes/Controls.xaml:70). The resulting foreground/background contrast is approximately **1.50:1**. Primary actions therefore change from a readable colored button to dark text on a dark hover background.

SecondaryButton hardcodes the dark background `#1B2638` at [Controls.xaml:74](C:/Users/user/animeapp/UniversalMediaOS.WPF/Themes/Controls.xaml:74), but its dynamic foreground becomes `#334155` in light mode at [ThemeRuntime.cs:63](C:/Users/user/animeapp/UniversalMediaOS.WPF/Helpers/ThemeRuntime.cs:63). This combination has approximately **1.47:1** contrast. The navigation hover background `#1C2A3D` at [Controls.xaml:121](C:/Users/user/animeapp/UniversalMediaOS.WPF/Themes/Controls.xaml:121), combined with light-mode TextPrimary `#0F172A`, is similarly low at approximately **1.23:1**.

These figures were computed directly from the source sRGB colors using relative luminance; they are not inferred from screenshot brightness. Full running-app hover-state inspection remains part of the parent audit.

Practical fix: define background/foreground pairs for each variant and interaction state, with separate theme values where needed. Primary hover should retain readable foreground contrast; secondary surfaces and navigation hover surfaces should use theme resources instead of fixed dark colors.

## 5. P2 — Tab actions fall back to native button chrome in disabled states

Evidence: the move-left button at [MainWindow.xaml:245](C:/Users/user/animeapp/UniversalMediaOS.WPF/MainWindow.xaml:245), move-right button at [MainWindow.xaml:257](C:/Users/user/animeapp/UniversalMediaOS.WPF/MainWindow.xaml:257), and close button at [MainWindow.xaml:269](C:/Users/user/animeapp/UniversalMediaOS.WPF/MainWindow.xaml:269) declare colors but no custom Style or ControlTemplate. The shared button base at [Controls.xaml:27](C:/Users/user/animeapp/UniversalMediaOS.WPF/Themes/Controls.xaml:27) is keyed; there is no implicit application-wide Button style to apply it to these controls. They therefore retain native template state rendering despite the transparent Background declaration.

The parent audit inspected a freshly running app through computer-use and observed stark white backgrounds behind the disabled tab reorder arrows on dark tab headers. That running-app observation corroborates the source-level style omission. The parent also visually confirmed the crowded navigation and tiny dropdown pills described above.

Practical fix: apply a dedicated tab icon button style with an explicit template and coherent normal, hover, pressed, focus, and disabled colors. Verify the first tab's disabled left arrow, the last tab's disabled right arrow, and a single tab with both arrows disabled. A custom button background alone does not control native template state chrome.

## Coverage and limits

The settings page itself still declares separate navigation and content columns at [SettingsView.xaml:105](C:/Users/user/animeapp/UniversalMediaOS.WPF/Views/SettingsView.xaml:105). The evidence does not support claiming that every settings control accidentally shares one grid cell. The most direct explanation for the user's grouping complaint is the shell strip in finding 1.

Searches across the test directory found no rendered-geometry assertions covering ActualWidth, DesiredSize, BoundingRectangle, screenshot comparison, or overlap detection. Passing these checks would not demonstrate that the layout or shared control templates render correctly.

The first repair pass should verify navigation and control sizes at 900 and 1280 DIP, each supported UI density, and the supported 90–140% content scale range. Inspect default, hover, focus, selected, and disabled states in both themes. Arabic uses right-to-left flow and should be included in visual verification. These are targeted validation recommendations; no additional extensive tests were run for this report.
